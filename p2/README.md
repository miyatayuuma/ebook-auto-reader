# P2.1 Pixel 9での確認

対象はPixel 9／Android 17のGoogle Play版DMMブックスと日本語縦書きリフロー本文です。DMMブックスの実画面を端末で取得できるかを最初に確認します。Androidのウィンドウ単位の画面取得が保護画面を返した場合は停止します。画像と文字認識結果はセッション中のメモリに置き、合成音声はアプリの一時領域から再生後に削除します。 [Android画面取得API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#takeScreenshotOfWindow(int,java.util.concurrent.Executor,android.accessibilityservice.AccessibilityService.TakeScreenshotCallback))

## 1. APK導入と画面取得

管理PCでP2ブランチを取得します。以下の `RUN_ID` はP2 Draft PRに表示された **P2 Reader** の成功したActions実行の番号です。

```bash
cd ~/ebook-auto-reader
git fetch origin
git switch --track origin/p2/reader-engine
adb devices -l
bash p2/install-debug.sh --run RUN_ID
```

複数台を接続している場合は、Pixel 9のシリアルを指定して `ANDROID_SERIAL=SERIAL bash p2/install-debug.sh --run RUN_ID` のように実行します。すでにブランチを取得済みなら `git switch p2/reader-engine && git pull --ff-only` へ置き換えます。APKをActions画面から取得した場合は、ZIPを展開し `--apk /path/to/reader-debug.apk` を使えます。ローカルで作成する場合は `python p1/fixtures.py --dense` と `python p1/reading.py prepare` を実行してから `gradle -p android :reader:assembleDebug` を実行します。モデルを転送せず画面取得だけ確認する場合は、末尾に `--probe-only` を加えます。

1. 起動したEbook Auto Readerからアクセシビリティ設定を開き、Ebook Auto Readerを有効にします。
2. DMMで縦書きリフロー本文を開き、メニューを閉じます。画面端の **▶** をタップして **画面取得テスト** を押します。
3. 「画面取得に成功」が表示されたときは次の手順へ進みます。制限、黒画面、取得失敗が表示されたときは、その結果を記録してください。

管理PCには `adb`、`gh`（Actionsから取得する場合）、`keytool`、`openssl` と Android SDK Build Tools 35.0.0 の `apksigner` が必要です。CI APKを管理PCで専用のデバッグ鍵に署名し直して導入します。鍵の既定の保存先は `~/.local/share/ebook-auto-reader/` です。既に導入済みの場合は同じ管理PC・同じ鍵で `bash p2/install-debug.sh --apk ~/Downloads/EbookAutoReader-P2.1.apk` を実行します。別の鍵ディレクトリを使用していた場合は、同じ `P2_SIGNING_DIR` を指定します。スクリプトは `adb install -r` で更新し、端末のモデルはサイズ・SHA-256が一致すれば再利用します。P1の `io.github.ebookautoreader.lab` とP2デバッグ版の `io.github.ebookautoreader.debug` は別アプリです。

## 2. 自作ページとDMMで再生を確認

画面取得だけを確認した場合は、同じコマンドから `--probe-only` を外してモデルを導入します。

P1で用意した `p1/out/ndl-models/` を再利用します。モデルが別の場所にある場合は `P2_MODELS=/path/to/ndl-models` を指定できます。移行済みの各ファイルはサイズとSHA-256が一致すれば再転送を省略し、不一致時は転送・検証後に確定します。モデルがなければP1で構築済みのPython 3.12環境で [P1のモデル取得手順](../p1/README.md) を実行します。

1. 音声一覧から日本語オフライン音声を選び、速度・高さを変えて試聴し、保存します。アプリを開き直して設定が復元されたことを確認します。音声数と名称は端末の構成に応じます。
2. **自作ページで試す** を開き、**読み上げ開始** を押します。「夜が明けると、川岸の石は朝の光を反射し、水の流れが銀色に見えた。」が2ページにまたがる一文として読まれることを確認します。続けて章扉まで進め、画面が変わらない末尾で停止することを確認します。
3. DMMで購入済みの縦書き本文の途中を表示し、**読み上げ開始**。最初は2ページで、スワイプ1回が意図した方向の1ページに対応するかと、文の連続性を確認します。次に複数ページで試します。スワイプ方向が逆の場合は停止し、設定の「次ページは右方向にスワイプ」を切り替え、正しいページで開始してください。
4. 前のページの音声が流れている間に次ページが表示されたら **一時停止** を押します。音声が止まり、読み上げ位置のページが表示されることを確認します。**再開** では最後に確認した文頭から読みます。**終了** も表示を同期します。
5. 一時停止中に手動でページを変えてから **再開** し、移動前のセッションで自動ページ送りを続けないことを確認します。読み上げ中に本文へ触れると一時停止します。停止処理後のタップからDMMを操作できます。自動ページ送りは、操作前のウィンドウと画面署名を照合します。

結果の共有には「画面取得」「2ページ連結」「複数ページ」「停止同期」「音声設定」の可否と、表示されたエラーを記録してください。

## P2.1 操作パネルと診断

- 画面端の **▶** をタップしてパネルを開きます。アイコンを長押ししたままドラッグし、指を離すと最寄りの左右端に吸着します。上下位置も保存されます。
- 縦書きの認識中は「本文認識中 5/18 行」のように、そのページの処理済み領域数を確認できます。一時停止・終了を押すと認識を中断します。ネイティブ処理が戻るまでは新しい認識の開始を制限します。
- 最初の音声再生でパネルが折りたたまれます。アイコンをタップすると再び開きます。待機中・一時停止中は、パネルの外側でDMMのタップ、ページ送り、メニュー操作ができます。
- **文字量の多い自作ページで試す** から自作の縦書き18行・887字を最初に表示できます。この画面で開始→認識進捗→最初の音声→自動折りたたみを確認します。もう一度開始し、認識の途中で終了できることも確認します。既存のページまたぎ試験は **自作ページで試す** から始めます。
- DMMではアイコンを左右に移動し、アプリを開き直して左右・上下位置を確認します。パネルの折りたたみ中と展開中に画面取得テストを行うには、展開してテストを開始し、一方は取得中に折りたたみます。操作パネルの文字が認識対象に混入していないことと、待機中・一時停止中にDMMメニューを開けることを確認します。

Pixelに接続した状態で、次のコマンドを実行してから再現します。添付する場合はこのタグで絞ったログと画面の状態表示を共有できます。

```bash
adb logcat -v threadtime -s EbookReader:I
```

ログでは `capture`、`ocr stage=MODEL/DETECT/RECOGNIZE/LAYOUT`、`tts connect/synthesize` の開始・終了を区別します。OCRは検出・認識予定・認識済み・除外の領域数と、前後のPSS・ネイティブ/Javaヒープを記録します。操作ジョブの開始・終了、ウィンドウの離脱と復元結果、タイムアウト時の処理段階も確認できます。ログに本文、画像、画面署名、発話内容は記録しません。

### 検証結果

- 旧版のコードではOCRの段階表示が次の処理を待つ間も残り得ました。画面取得コールバックには期限がなく、読み上げ開始時にオーバーレイを付け直す経路もありました。旧版の実機ログでは表面の再作成が複数回あり、TTSの切断ログは最後の記録より前に出ています。停止した処理の特定にはP2.1の実機診断ログが必要です。
- 公式のDEIM・PARSeqモデルと製品のKotlin認識・レイアウト処理をLinux x86_64、ONNX Runtime 1.23.2、AWTの画像処理を使って実行しました。23領域を検出し21領域を認識。自作の本文18行をすべて得ました。本文に3字の置換と、ノンブルの混入1行がありました。前処理で除外を有効にした場合と無効にした場合、および推論1・2スレッドの出力は一致しました。
- 2スレッドのウォーム測定3回の中央値は、領域検出1.18秒、文字認識2.34秒、処理合計3.70秒でした。1スレッドの合計中央値は4.94秒でした。両方の最大RSSは約795 MiB（JVM全体）。この差をもとにP2.1の推論は2スレッド、演算間のスレッドは1としました。Pixelでの所要時間とメモリは実機で計測します。Linuxで推論中のONNXへの中断要求が実際に推論を終了させることも確認しました。

## 発音辞書

アプリ内部の `files/pronunciation/books/<ID>.tsv` を書籍別、`files/pronunciation/common.tsv` を共通辞書として読みます。TSVはUTF-8で、1行は「表記、読み、直前の文字列、直後の文字列」のタブ区切りです。共通辞書には少なくとも片側の適用条件を指定します。書籍別のIDは設定で選び、デバッグ版では管理PCから転送できます。

```bash
adb -s SERIAL shell -T run-as io.github.ebookautoreader.debug mkdir -p files/pronunciation/books
adb -s SERIAL shell -T run-as io.github.ebookautoreader.debug sh -c \
  "'cat > files/pronunciation/books/sample.tsv'" < /path/to/sample.tsv
```

ルビは推定した親語の範囲に付け、確信のあるものだけ使用します。書籍別辞書、条件付きの共通辞書が続き、残りはGoogle TTSの読み推定を使います。形態素解析の補正は根拠を検証した実装に差し替えられる構造です。P1の評価専用ルールは製品に含めません。

## P2の判定範囲

- 先読みは次の1ページと次の音声1件です。画像から一様な明色と判定し、検出領域もない白紙は、隣接する1枚に限って通過を試みます。図表は高確信の領域を検出した場合に短い音を鳴らし、認識できたキャプションを続けます。
- 再開位置は音声ファイルの実再生を起点にした文頭です。再生の経過時間を測り、完了はMediaPlayerの完了イベントから確定します。停止時は確認済みの画面署名と逆方向の操作を照合します。読書中は表示を維持し、画面ロックや対象ウィンドウの変更で停止します。
- ルビの親語は画像上の幾何情報から保守的に推定します。P1のNDL認識器を共有し、縦書きの段・列、柱とノンブル、本文・ルビ・図版の判定を追加しました。上流CLIの一般紙面向けXML読み順、表の構造化、縦中横補正、長い行の分割認識はP3の検証対象です。100文字用モデルで終端を確認できない本文候補は停止します。
- OCRコードは国立国会図書館のNDLOCR-Lite 2.0.0の入力・出力に合わせたAndroid移植です。モデルをアプリやActions成果物に同梱せず、P1の取得手順で利用します。 [上流パッケージ](https://pypi.org/project/ndlocr-lite/2.0.0/) ／ [上流ソースとライセンス](https://github.com/ndl-lab/ndlocr-lite)
